# confetti-mcp — Final Prioritised Audit Report

**Date:** 2026-08-15
**Scope:** `DeviesDevelopment/confetti-mcp` @ `main` (all work merged), plus the coupling
surface into `confetti@4.1.5` and the Azure/Docker Hub deployment path.
**Method:** multi-lens read of all 11 source + 9 test files, with every finding below
having survived independent adversarial verification (33 raw survivors, 6 refuted,
deduped here to **29**).

---

## Summary

| Severity | Count |
|----------|-------|
| Critical | 1 |
| Important | 7 |
| Minor | 21 |
| **Total** | **29** |

**Overall health: good.** This is a small, disciplined codebase that does the hard
things right. Per-request statelessness, header-first API-key handling, exact-match key
redaction, an enforced (non-advisory) connect-URL filter that gates `tools/call` as well
as `tools/list`, a typed `RESOURCE_MAP` deliberately built to fail the build on upstream
renames, and 111 passing tests including drift guards on the 63-tool count — all present
and working. Several high-value security bugs were already found and fixed before this
audit (404 key leak, ops-filter fail-open on repeated params, connection-key override
from tool args, healthcheck/port/version hardcoding). The refuted list below shows the
audit did not have to reach for material.

The findings that remain cluster in four honest gaps:

1. **Input validation the enforced filter depends on** — one path-traversal hole
   (rank 1) lets a `resources=events` connection reach and *delete* other resources,
   defeating the very filter the code works hard to make non-advisory.
2. **A dependency-level data-isolation defect** — `confetti`'s process-global yayson
   `Store` (rank 6) can, under the right id collision, splice one tenant's fetched
   record into another's response, and retains all records for the life of the process.
   This is the one finding that can falsify the server's central promise; it is scored
   critical but its live exploitability is unproven (see the finding for the precise
   precondition).
3. **Missing time/space bounds on a public multi-tenant proxy** — no working upstream
   timeout, no per-call log line, an inert Azure health probe.
4. **Deploy-path trust** — a mutable Docker Hub tag with webhook auto-deploy is the
   production trust root, and the image is never executed before it ships.

None of these are the result of sloppiness; most are conscious deferrals or thin-layer
assumptions that a live public deployment now makes worth closing. Nothing here suggests
the design is unsound.

### Reconciliation with the known-deferred list

No survivor below is merely a re-prioritised known-deferred item — each was checked
against `known-deferred.txt` and is distinct. One overlap worth calling out: the
regression test recommended inside **rank 6 (yayson store)** is the same
*cross-request isolation test* recorded as known-deferred item 13. That item was filed
as "the property holds by inspection." This audit found evidence it may **not** hold by
inspection at the dependency layer, so I am explicitly **re-prioritising that test
upward** from "nice to add" to "the cheapest step toward the single most
security-relevant invariant of the server." The `ID_SCHEMA` finding (rank 15) is *not*
a re-report of known-deferred item 5 — that item is about reference-sharing/mutation of
the shared schema object; rank 15 is about the `['string','number']` union type tripping
strict clients.

---

## DO THESE FIRST

1. **Rank 1 — Validate the `id` argument.** A one-line allowlist (`/^[A-Za-z0-9_-]+$/`)
   in `requireId` closes a path-traversal hole that lets a filtered connection `DELETE`
   resources it was scoped away from. Highest risk-per-effort in the report.
2. **Rank 2 — Emit `required` for filter-mandatory findAll tools.** Three core tools
   (tickets, payments, ticket batches) currently guarantee a `ZodError` on the first
   schema-conformant call. Trivial generator fix.
3. **Rank 3 — Move the `filter.status` enum onto `items`.** As shipped, the schema is
   unsatisfiable; status filtering on tickets/payments is impossible from any validating
   MCP client. Two-line post-process.
4. **Rank 4 — Invert the connection-option denylist to an allowlist.** Same vulnerability
   class that was already fixed once (the `apiHost` redirect); the denylist fails *open*
   against the next upstream option key. Small, fail-closed.
5. **Rank 5 — Put a real deadline around `callTool`.** `confetti`'s 5s/15s timeout is
   silently dead under node-fetch v3, so a hung upstream pins connections and memory
   unboundedly on a public server with no logging to see it.

## Prioritised findings

Ordered by (real risk × likelihood) ÷ effort — do rank 1 first.

### 1. Unvalidated `id` enables URL path traversal that bypasses the enforced `?resources=` filter
- **Severity:** important · **Effort:** small
- **Files:** `src/tools/dispatch.ts:22-26` (`requireId`), used at `:72, :79, :83`;
  schema `src/tools/definitions.ts:33`

**What is wrong.** `requireId` only type-checks; it accepts empty strings and strings
containing `/`, `..`, `?`, `#`. The id is interpolated raw into the upstream URL path
(`${models.event.path}/${id}`) and node-fetch's WHATWG URL parsing collapses dot
segments. Verified empirically: `id:"../payments/7"` on `confetti_events_find` issues
`GET /payments/7`; `id:""` issues `GET /events/` (the collection route).

**Failure it causes.** An operator scopes an agent `?resources=events&ops=delete`. A
prompt-injected or hallucinating model calls `confetti_events_delete` with
`{"id":"../payments/7"}`; the request normalises to `DELETE /payments/7` **with the real
API key attached**, destroying a record the connection was configured never to touch.
`mcp.ts:58-64` exists specifically so the filter is "not advisory" — this defeats that
guarantee on the `resources` dimension for every id-bearing tool, including the
destructive ones.

**Fix.** In `requireId`, reject empty/whitespace ids and any containing `/ \ ? #` or a
`..` segment — or allowlist `/^[A-Za-z0-9_-]+$/`, which covers Confetti's numeric ids and
hashids — throwing the existing `ParameterError` shape.

### 2. Generated `findAll` schemas omit required filters — three tools advertise a contract that always fails
- **Severity:** important · **Effort:** small
- **Files:** `src/tools/definitions.ts:56-91` (`findAllSchema`); upstream
  `confetti-node/src/utils/to-json-schema.ts:60-83`, `.../schemas/ticket.ts:221-223`

**What is wrong.** `findAllSchema` never reads `BaseFilter.required` and never marks the
`filter` property required. But `ticket`, `payment`, and `ticketBatch` make
`filter.eventId` mandatory upstream, enforced by an unconditional `.parse` in
`resources.ts`. Verified: `confetti_tickets_find_all`, `confetti_payments_find_all`,
`confetti_ticket_batches_find_all` publish no `required` array anywhere, yet
`callTool(ticketsFindAllTool, {})` throws `ZodError` (`filter` required) with no network
involved.

**Failure it causes.** A model calls `confetti_tickets_find_all` with `{}` — fully
conformant to the advertised schema — and gets an invalid-parameters error on the first
try. Every session pays a wasted round-trip; stricter clients that pre-validate can never
prompt the user for `eventId` up front.

**Fix.** In `findAllSchema`, collect filter keys where `filter.required === true` into a
`required` array on the filter object schema, and add `required:['filter']` at the top
level when any exist. The flags are already on the entries the loop iterates.

### 3. `filter.status` schemas on tickets/payments are unsatisfiable (enum on the array, not its items)
- **Severity:** important · **Effort:** trivial
- **Files:** `src/tools/definitions.ts:63`; root cause
  `confetti-node/src/utils/to-json-schema.ts:69-79`

**What is wrong.** Both tools publish
`filter.status = {"type":"array","items":{"type":"string"},"enum":["attending",…]}`. In
JSON Schema, `enum` at the array level means the array **instance** must equal one of the
listed strings — so no value validates. Verified with ajv: `["attending"]` → false
("must be equal to one of the allowed values"), `"attending"` → false ("must be array"),
`[]` → false. These are the only two array-with-top-level-enum sites in all 63 tools.

**Failure it causes.** A schema-validating MCP host (VS Code MCP, mcp-inspector, several
gateways) rejects every `confetti_tickets_find_all` / `confetti_payments_find_all` call
carrying a status filter, before it reaches the server. There is no argument the model
can construct that passes. Non-validating clients get a contradictory schema (array type,
string enum) that degrades tool use.

**Fix.** Post-process in `findAllSchema`: when a generated filter property has
`type:'array'` with a top-level `enum`, move the enum into `items`
(`items:{type:'string', enum:[…]}`). Or fix `filterToJsonSchema` upstream and bump.

### 4. Connection-option denylist fails open against upstream option additions
- **Severity:** important · **Effort:** small
- **Files:** `src/tools/dispatch.ts:47-53` (`RESERVED_OPTION_KEYS`), `:68-73` (merge sites)

**What is wrong.** `RESERVED_OPTION_KEYS = ['apiKey','apiHost','apiProtocol','raw']` is a
hand-maintained mirror of `confetti`'s `baseOptionsSchema`. The find/findAll paths merge
caller tool arguments straight into the options object and strip only these four keys.
`confetti`'s option schemas are zod *strip* objects, so unknown keys are discarded
**today** — but the moment a minor/patch adds a new connection-affecting key to
`baseOptionsSchema`, that key becomes settable from tool arguments with no compile error
and no failing test. `baseOptionsSchema` is not exported (`exports` maps only `.`), so the
denylist cannot even be drift-tested against it.

**Failure it causes.** This is the exact class already fixed once (the `apiHost` redirect
that ships the caller's real key to an attacker host). `confetti 4.2` adds e.g.
`basePath` or `apiVersion`; lockfile bumps, all 111 tests pass, and a prompt-injected
call to `confetti_events_find_all` can now set it — with the caller's real key attached.
Tool arguments are the least-trusted, prompt-injectable input; a security boundary here
should fail closed.

**Fix.** Invert to an allowlist at the two merge sites: findAll passes only
`{filter, sort, include, page}`, find passes only `{include}` — precisely the keys the
generated schemas advertise. Any future upstream option key is then inert by
construction.

### 5. No effective upstream timeout — `confetti`'s timeout is silently dead under node-fetch v3
- **Severity:** important · **Effort:** small
- **Files:** `src/server/mcp.ts:72`, `src/tools/dispatch.ts:55-89`; root cause
  `confetti-node/src/adapter.ts:78` + node-fetch 3.3.2

**What is wrong.** `confetti`'s adapter passes `timeout: get?5000:15000` into node-fetch,
but node-fetch **v3 removed the `timeout` option** (it reads only `signal`). Verified: a
request with `timeout:500` against a blackhole server was `STILL HANGING after 8s`. No
`AbortSignal` is used anywhere; `mcp.ts:72` awaits `callTool` with no deadline. The
`confetti` code *looks* guarded, which is why a pure source read concludes calls are
bounded at 5s/15s — they are not. `app.ts:63` closes the transport on client disconnect
but aborts nothing upstream.

**Failure it causes.** On a public multi-tenant proxy, a slow/blackholed
`api.confetti.events` turns every in-flight `tools/call` into a long-lived leak — client
connection + `Server`/transport pair + upstream socket held until TCP gives up (Azure
cuts the client at ~230s idle but not the outbound socket). Under load with a degraded
upstream, stuck requests accumulate; this is the only real unbounded-memory path in an
otherwise well-bounded process, and no `confetti` bump surfaces it.

**Fix.** Immediate, in-repo: race the `await callTool(...)` against
`AbortSignal.timeout(~20-30s)` returning a clean `isError` result, freeing the MCP
request/transport. Proper: file an upstream fix so `confetti` passes an `AbortSignal` to
node-fetch v3, and propagate the client-disconnect abort from `res.on('close')`.

### 6. Process-global yayson `Store` can bleed one tenant's records into another's response (and never frees memory)
- **Severity:** critical · **Effort:** medium
- **Files:** root cause `confetti/dist/adapter.js:8,59` (module-scope
  `const store = new Store()`, `store.sync(body)` per response); reachability
  `src/tools/dispatch.ts:12-20,47` (never sets/allows `raw`), `src/server/mcp.ts:72`
- **Lenses:** auth/credential handling + attack surface (two independent verifications
  merged here)

**What is wrong.** `confetti` builds its JSON:API deserializer once at module scope and
calls `store.sync(responseBody)` for **every** response across **every** request in the
process. yayson's `Store` (1) accumulates records for the life of the process, deduped
only by `(type,id)`, never reset between requests, and (2) resolves relationship
references by scanning **all** previously-synced records via `findRecord()`. So a
relationship on request B that references, say, `{contact,5}` but does not `include` it is
resolved from whatever `{contact,5}` request A synced earlier — A's attributes are spliced
into B's result. `confetti-mcp` never passes `raw:true` (it is even in
`RESERVED_OPTION_KEYS` and stripped), so `store.sync` always runs.

Two verifiers reproduced the bleed against the shipped builds: tenant A fetched a private
record, tenant B (different key) then fetched a resource whose linkage-only relationship
pointed at A's id with no `included` — and B's tool result contained A's private
attributes (`"email":"alice@tenant-a.example"`, `internalNote:"A-only-data"`). A control
sync into a fresh `Store` returned only the bare stub, proving the extra data came from
the shared store.

**Failure it causes.** Cross-tenant disclosure of fetched records on a live multi-tenant
deployment — directly falsifying the server's central "no shared per-user state"
promise. Independently: unbounded memory growth (Always On, no restart) and O(N)→
quadratic `sync` cost as `records` grows, giving any single caller a lever to degrade the
shared process.

**Honest exploitability caveat.** The bleed requires a cross-tenant `(type,id)` collision
**plus** an un-included relationship reference. Sample IDs across all models are large
global sequences (`16500`, `210644`, `3344691`), which would *prevent* collision on
distinct records if the live API allocates ids globally. This is verified in code but
**not** against the live API — which is exactly why the very first step is a test, not a
rewrite. The unbounded-memory half holds regardless of id allocation.

**Fix.** `confetti-mcp` cannot fix a dependency singleton from outside. In priority order:
(a) **add the cross-request isolation regression test** — two concurrent connections,
different keys, a relationship reference to a colliding id, assert no bleed. This is
known-deferred item 13, re-prioritised upward here; it both confirms/refutes live
exploitability and pins the invariant. (b) File/patch `confetti-node` so each call
constructs its own `new Store()` (or `store.reset()` before each `sync`). (c) As a
stopgap fully in `confetti-mcp`'s control, pass `raw:true` on upstream calls so responses
bypass `store.sync` entirely — note this changes the response shape callers see, so it is
a product decision, not a free win.

### 7. Released image is never executed before it is pushed and auto-deployed
- **Severity:** important · **Effort:** small
- **Files:** `.github/workflows/release.yml:30-67`, `.github/workflows/ci.yml:43-50`

**What is wrong.** The release job runs lint + 111 tests against source compiled by the
runner's Node 22 on Ubuntu (glibc), then builds a **separate** artifact inside
`node:22-alpine` (musl, independent `npm ci`) and pushes that. The image that ships is not
the artifact that was tested, and **nothing** ever starts the container — no `docker run`,
no healthcheck poll, no request to `/mcp`. The `linux/arm64` variant is built under QEMU
and has executed nothing before publish. Combined with the webhook (next finding), a
broken image goes straight to production.

**Failure it causes.** A whole class of image-only failures — a file missing from the
`COPY` list, `npm ci --omit=dev` resolving differently, a bad `CMD`/`ENTRYPOINT`, a
PORT/env issue — passes `npm test` and ships. The first execution of the published image
is in production; the container crash-loops or 500s on Azure with nothing in the git diff
to explain it.

**Fix.** Between build and push, build `linux/amd64` locally (`load:true, push:false`),
`docker run -d` it, poll the health endpoint and make one bad-key `/mcp` request
(expecting the JSON-RPC error is enough), fail the job on non-2xx, then run the
multi-platform build-and-push. ~10 lines of YAML closes the "never booted" gap for the
platform Azure runs.

### 8. Docker Hub webhook makes a mutable registry tag the production trust root
- **Severity:** important · **Effort:** medium
- **Files:** `.github/workflows/release.yml:48-56`; deploy path (Docker Hub webhook →
  Azure re-pull)

**What is wrong.** Production deploys when Docker Hub fires a webhook and Azure re-pulls
the tracked tag. Every tag the release pushes (`{{version}}`, `{{major}}.{{minor}}`,
`sha`) is mutable; no digest pinning, no signature/attestation verification, no human
approval gate between "bytes on Docker Hub" and "bytes in production." Anyone who can push
to `deviesdevelopment/confetti-mcp` — a leaked `DOCKERHUB_TOKEN` (long-lived GitHub
secret), a compromised Docker Hub account, or Docker Hub itself — can overwrite the tag
and have Azure auto-run their image. The design doc (`docs/…/design.md:52-63`) planned the
safer pinned-digest + Azure-OIDC deploy repo and deferred it; the deployed path is
materially weaker than the design's own stated posture.

**Failure it causes.** This server receives every caller's Confetti API key in the
`Authorization` header. A malicious image is a transparent credential-harvesting proxy —
forward to the real API so nothing looks broken, exfiltrate every key. The server's
stateless design does not protect against this; the trust boundary has moved to Docker
Hub.

**Fix.** Short term: scope `DOCKERHUB_TOKEN` to a fine-grained, push-only, single-repo
token and enable org 2FA (both small). Real fix: implement the deferred private deploy
repo — disable the webhook, pin App Service to an image **digest**, and roll out via an
explicit Azure-OIDC workflow taking the digest as input.

### 9. `withDefaultPage` silently discards a non-object `page` instead of letting validation reject it
- **Severity:** minor · **Effort:** trivial
- **Files:** `src/tools/dispatch.ts:28-31`

**What is wrong.** `page:"2"` or `page:2` (a plausible model shorthand) fails the `typeof`
check and is replaced with `{size:25}`. The call then succeeds with **page-1** results
instead of surfacing the clear `expected object` `ZodError` the upstream schema would have
produced. Verified: `events.findAll({page:2,…})` throws that `ZodError` upstream today.

**Failure it causes.** The worst pagination failure mode — the model asked for page 2,
silently gets page 1, no signal — so it loops re-fetching the same 25 records or concludes
records don't exist.

**Fix.** Only default when `page === undefined`; forward any other value untouched so
`pageOptionsSchema.parse` rejects non-objects with an actionable error.

### 10. Caller pagination is never clamped — single-request response amplification
- **Severity:** minor · **Effort:** small
- **Files:** `src/tools/dispatch.ts:28-31, 67-69`; `src/server/mcp.ts:72`

**What is wrong.** `withDefaultPage` only *defaults* an omitted page; any caller
`page.size`/`page.limit` overrides it with no upper bound, and upstream `pageOptionsSchema`
declares them `z.number().optional()` with no `.max()`. The full response is buffered,
denormalized, and re-serialized with `JSON.stringify(result,null,2)` (pretty-print inflates
memory/CPU). This is a deliberate design choice for *client context* reasons, but it also
has no *server-memory* bound, and it compounds rank 6's unbounded store.

**Failure it causes.** A valid-key caller issues `findAll` with
`{page:{size:1000000}}` concurrently, spiking memory on the shared process; response size
is bounded by the key's own tenant data, but co-tenant availability suffers.

**Fix.** Clamp `page.size`/`limit` to a sane `MAX_PAGE_SIZE` in `withDefaultPage` rather
than only defaulting when absent; drop the 2-space pretty-print on tool results.

### 11. Tool-call failures are never logged server-side — on-call is blind
- **Severity:** minor · **Effort:** small
- **Files:** `src/server/mcp.ts:54-86`, `src/server/app.ts:78,91`

**What is wrong.** Total production log output is one startup line (`main.ts:8`) and one
500-handler line that records only `error.name`. Every tool-call error — upstream 5xx,
DNS failure, auth rejection — is caught and returned only to the client (`mcp.ts:82`); the
server records nothing. The zero-request-logging stance is a deliberate, documented
decision to keep URL-carried keys out of logs, but it is over-broad: it suppresses all
telemetry, not just URLs. `LOG_LEVEL` exists in config but is documented as unwired
(`README.md:157`).

**Failure it causes.** When a user reports "it stopped working," on-call cannot
distinguish no-traffic vs auth 4xx vs every-upstream-call-failing vs wedged process — logs
are identically empty. Combined with rank 5, an upstream incident is invisible from the
server side. (Note: App Service platform metrics still record request counts/latency, so
"no evidence a request arrived" overstates it — but cause-of-failure is genuinely absent.)

**Fix.** One structured, key-free line per tool call: tool name, operation, outcome
(ok / error name / upstream status class), duration — never URL, arguments, or key. The
existing `redact()` in `errors.ts` can second-net any logged detail; optionally wire
`LOG_LEVEL`.

### 12. Docker `HEALTHCHECK` is inert on Azure App Service; no platform health check configured
- **Severity:** minor · **Effort:** trivial
- **Files:** `Dockerfile:19-20`

**What is wrong.** Azure App Service for Containers does not execute Docker `HEALTHCHECK`
instructions — health probing there is the separate App Service "Health check" feature (a
configured path), which the stated Azure config does not include. The `HEALTHCHECK` only
works under plain Docker/compose. (The `/` target itself is fine — static, dependency-free,
tools built before `listen`.)

**Failure it causes.** A container that is listening but wedged (per rank 5) is never
detected or restarted by the platform; Always On only keeps it warm. The site stays down
until a human restarts it.

**Fix.** Enable App Service Health check pointing at `/` (`healthCheckPath:"/"`); keep the
Dockerfile `HEALTHCHECK` for local use and document that Azure ignores it.

### 13. Malformed / oversized request body returns HTTP 500 `-32603` instead of 400 `-32700`
- **Severity:** minor · **Effort:** small
- **Files:** `src/server/app.ts:20,90-93`

**What is wrong.** `express.json()` throws `SyntaxError` (`status 400`,
`type:'entity.parse.failed'`) for unparseable bodies and `PayloadTooLargeError` (413) for
bodies over the 4mb limit. The final handler hardcodes `res.status(500)` + JSON-RPC
`-32603`, ignoring `error.status`, and lacks the standard `res.headersSent` guard.
Verified: `{invalid json` → 500 `-32603` with a `level:error msg:unhandled` log line.
(Distinct from known-deferred items 12/21, which concern a different, unreachable throw
site and its missing test — this handler path is trivially caller-triggerable.)

**Failure it causes.** A client typo is reported as a server fault; retry-on-5xx logic
retries a permanently-bad request indefinitely, and the error log fills with attacker- or
typo-triggerable "unhandled SyntaxError" entries that mask real 500s.

**Fix.** In the handler: `if (res.headersSent) return next(error)`; then branch on
`error.type === 'entity.parse.failed'` → 400 `-32700`, `entity.too.large` → 413, logging
at warn; keep 500 `-32603` as fallback. Add the two tests beside the existing 404 test.

### 14. Unknown tool on `tools/call` returns an `isError` result instead of the spec's `-32602`
- **Severity:** minor · **Effort:** small
- **Files:** `src/server/mcp.ts:57-68`

**What is wrong.** An entirely unknown tool name returns
`{isError:true, content:[{type:'text', text:"Unknown tool '…'"}]}`. The MCP spec gives
"Unknown tools" as its canonical **protocol** error (JSON-RPC `-32602`); the SDK's own
`McpServer` throws `McpError(InvalidParams)` here. `isError` is defined for tool
*execution* failures the model should react to. (The `isError` refusal for *filtered*
tools at `:62-63` is defensible — its message is meant for the model — but the plain
unknown-tool branch has no such rationale.)

**Failure it causes.** A client keying on `-32602` to detect a stale tool list (refresh
`tools/list`, strip a hallucinated tool) never sees the signal and feeds "Unknown tool"
back to the model, which loops retrying variations.

**Fix.** In the unknown-name branch throw `new McpError(ErrorCode.InvalidParams, …)`. Keep
the filtered-tool `isError` if intended, documented as a deliberate deviation.

### 15. `ID_SCHEMA` union type `['string','number']` trips strict validators and LLM-bridge clients on 41 tools
- **Severity:** minor · **Effort:** trivial
- **Files:** `src/tools/definitions.ts:33` (used at `:94,:122,:131`)

**What is wrong.** `ID_SCHEMA = {type:['string','number']}` appears in 41 of 63 schemas
(every find/update/delete). Valid JSON Schema, but the only construct in the whole surface
that strict consumers reject: ajv strict mode refuses to compile it without
`allowUnionTypes` (verified — it is the sole `strictTypes` failure), and hosts bridging to
Gemini/OpenAI single-type function declarations drop the field's typing or reject the tool.
(Distinct from known-deferred item 5, which is about reference-sharing of the schema
object.)

**Failure it causes.** On a sanitising host the id parameter silently loses its type and
description; on a rejecting host, 41 of 63 tools disappear or error at registration,
leaving only `find_all` and `create` usable.

**Fix.** `ID_SCHEMA = {type:'string', description:'Identifier of the record.'}` —
`requireId` already accepts strings and ids serialize into a URL path where string/number
are equivalent.

### 16. `annotations.title` repeats the machine name instead of a human title
- **Severity:** minor · **Effort:** trivial
- **Files:** `src/tools/definitions.ts:165-174`

**What is wrong.** `annotate()` sets `title: name`, so every tool ships
`annotations.title` equal to its snake_case name (`confetti_sponsor_levels_delete`). The
spec defines `annotations.title` as a human-readable UI title, and hosts prefer it over
`name` for display. As shipped it is pure duplication across all 63 tools. (All other
annotations — `readOnlyHint`, `destructiveHint`, `idempotentHint` — are correct.)

**Failure it causes.** Approval dialogs and tool pickers show
`confetti_sponsor_levels_delete` where the annotation exists to show "Delete Sponsor
Level."

**Fix.** Build a title from pieces already in hand — verb map
`{findAll:'List',find:'Get',create:'Create',update:'Update',delete:'Delete'}` + `m.name` —
or drop the `title` annotation and let hosts fall back to `name`.

### 17. `npm ci` runs dependency lifecycle scripts during image build and CI
- **Severity:** minor · **Effort:** trivial
- **Files:** `Dockerfile:4,14`; `ci.yml:22`, `release.yml:30`

**What is wrong.** `npm ci` without `--ignore-scripts` runs every transitive package's
install/postinstall with network access — in the release case inside the build that
produces the production image. Lockfile scan confirms **zero** production packages have
install scripts (only dev-only `esbuild`/`fsevents`), so disabling scripts is functionally
free.

**Failure it causes.** A compromised transitive merged via a green Dependabot PR detonates
its postinstall inside `npm ci --omit=dev`, planting a payload the integrity-checked
tarball never contained. `--ignore-scripts` downgrades that worst case from arbitrary
build-time code execution to (at most) bad JS running at runtime.

**Fix.** `npm ci --ignore-scripts` in both Dockerfile stages and both workflows.

### 18. Base image `node:22-alpine` is unpinned — builds are not reproducible
- **Severity:** minor · **Effort:** trivial
- **Files:** `Dockerfile:1,9` (and `:15` `apk add tini`)

**What is wrong.** Both stages use `FROM node:22-alpine` with no digest, so every release
absorbs whatever the tag points to; two builds of the same git tag can differ. App deps
are byte-locked via `package-lock.json`; the OS/runtime under them is not.

**Failure it causes.** A `node:22-alpine` refresh ships a regressed musl/OpenSSL; the next
release rebuilds on it, tests still pass on the glibc runner (rank 7 — the image is never
executed), it auto-deploys, and TLS/DNS behaviour changes with nothing in the diff.

**Fix.** Pin both `FROM` lines to `node:22-alpine@sha256:…` (same digest for both stages)
and let Dependabot/Renovate bump the digest deliberately. (Only worth doing alongside an
update bot — a frozen digest with no bot trades a patch regression for guaranteed
staleness.)

### 19. GitHub Actions pinned to mutable major tags while the release job holds the registry credential
- **Severity:** minor · **Effort:** small
- **Files:** `.github/workflows/release.yml:14-59`, `ci.yml:15-44`

**What is wrong.** All actions are pinned to mutable major tags (`@v4`, `@v3`, `@v6`), not
commit SHAs. These are GitHub/Docker-maintained (low hijack probability), but the impact
is amplified: `release.yml` exposes `DOCKERHUB_TOKEN` to the `docker/*` actions, and the
webhook auto-deploy (rank 8) means a hijacked tag can push an image that immediately runs
in production and sees user keys.

**Failure it causes.** A force-pushed `docker/login-action@v3` tag (the tj-actions
pattern) runs on the next `v*` release, reads `DOCKERHUB_TOKEN` from its inputs and
exfiltrates it; the attacker then pushes a trojaned image that the webhook deploys.

**Fix.** Pin actions to full commit SHAs with a version comment, at minimum in
`release.yml`; add `.github/dependabot.yml` (github-actions ecosystem) to keep SHAs fresh.

### 20. End-to-end key redaction is unwire-able without any test failing
- **Severity:** minor · **Effort:** small
- **Files:** `src/server/mcp.ts:82`; tests `test/tools/errors.ts`, `test/server/mcp.ts`

**What is wrong.** Exact-match redaction of the caller's key exists only because
`mcp.ts:82` passes `options.context.apiKey` as the third arg to `toolErrorMessage`. No
test drives an upstream error whose message contains the caller's key through the full
server and asserts the `isError` body omits it. Verified: deleting that third argument

**Failure it causes.** A refactor drops/reorders the `toolErrorMessage` args (it works

**Fix.** One integration test in `test/server/mcp.ts`: connect with a **non-`sk_`** bearer
key, nock an upstream 401/500 with the key in the body, call a tool, assert the `isError`

### 21. The cannot-redirect guard covers only 2 of 5 operations
- **Severity:** minor · **Effort:** small
- **Files:** `test/tools/dispatch.ts:125-173`, `test/server/mcp.ts:151`

**What is wrong.** The reserved-key regression tests pin "tool args cannot redirect the
upstream call" only for `findAll` and `find`. `create`/`update`/`delete` have no
equivalent guard. They are safe **today** by construction (dispatch passes options as a

### 22. The no-logging canary only intercepts `console.*`, not stdout/stderr writes

### 25. Static method call signatures are fully type-erased; only events/pages/contacts are pinned
- **Severity:** minor · **Effort:** small
- **Files:** `src/tools/dispatch.ts:60-63`, `src/confetti/resource-map.ts:39`

**What is wrong.** Both sites erase `confetti`'s real static signatures
(`(...args:never[])`/`(...callArgs:unknown[])`), so `tsc` gives zero protection if an
upstream bump changes any method's parameter order/arity. Runtime protection exists only
where nock tests exercise real calls (events findAll/find/create/update, pages delete,
contacts findAll). The count-based drift guards check only method *existence*, never
signature.

**Failure it causes.** `confetti 4.3` changes e.g. `formFields.update` to `(id, options,
json)`; `tsc` passes (all casts), 111 tests pass (count still 63), and
`confetti_form_fields_update` sends the body as options — zod strips every field and an
empty PUT goes out. Fails only at runtime for that one tool.

**Fix.** Cheapest: a drift test asserting `Function.length` for all 63 operations
(findAll=1, find=2, create=2, delete=2, update=3). Stronger: type the five dispatch
branches against real `confetti` signatures instead of `unknown[]`.

### 26. Generated schemas keep only `{properties, required}` from zod's JSON Schema output, with no sanity guard
- **Severity:** minor · **Effort:** trivial
- **Files:** `src/tools/definitions.ts:110-115`

**What is wrong.** `bodySchema` rebuilds each schema from only `properties` + `required`,
discarding every other top-level keyword and assuming the output stays a flat object schema
forever. `confetti` pins zod exactly (4.1.11) but controls that pin; a bump that introduces
`z.lazy`/reused sub-schemas can make `toJSONSchema` emit `$defs` with `$ref`s inside
properties — the `$defs` get dropped, producing dangling `$ref`s. Verified that the
same registry already contains a union-shaped model (`previewToken`) that violates the
flat-object assumption — it is only unreachable because it's not in `RESOURCE_MAP`. No
existing test would fail.

**Failure it causes.** A routine lockfile bump silently ships tool schemas with dangling
`$ref`s; schema-validating MCP clients reject or garble those tools, invisible in this
repo's CI.

**Fix.** Two-line test: assert `JSON.stringify` of all 63 definitions contains no `$ref`,
and every `inputSchema` has `type:'object'`.

### 29. Default-page-size test asserts the implementation constant, not the documented contract
- **Severity:** minor · **Effort:** trivial
- **Files:** `test/tools/dispatch.ts:34`; `src/tools/definitions.ts:37,40`

## DELIBERATELY NOT DOING

**Refuted during verification (do not action):**

- *URL keys captured by Azure platform logging* — restates the design's own twice-documented,
  consciously-accepted tradeoff (header is the default; URL carriers are discouraged
  fallbacks forced by the claude.ai web connector). No code-level remediation exists.
- *`redact()` skips secrets under 4 chars* — a deliberate, comment-and-test-pinned tradeoff;
  exact-matching a 1-3 char string against free text corrupts ordinary messages, and a
  sub-4-char "key" is not credential-grade. Matter of taste, not a defect.
- *Floating `node:22-alpine` with "every commit" auto-redeploy* — the causal chain is false:
  images build only on `v*` tags, the release path runs lint+tests first, and no workflow
  tests the built image, so pinning wouldn't make any tested artifact byte-identical. (The
  legitimate reproducibility sliver survives as rank 18.)
- *5s shutdown drain shorter than the 15s write timeout* — Azure SIGKILLs the container at
  ~5s (`WEBSITES_CONTAINER_STOP_TIME_LIMIT`), so the platform, not the in-code timer, is the
  binding deadline; raising the timer would be dead code ending in an unclean kill.
- *Tests fall through to the real production API on nock mismatch* — false for the pinned
  nock 14.0.10: an unmatched request to an origin with an active interceptor throws
  "Nock: No match" and hits no network. The claimed failure scenario produces the precise
  diagnostic the finding says is lost.
- *`confetti` is the only caret-ranged dependency* — the tool-surface tests hardcode the
  surface as literals (63 tools, 18 resources, per-verb counts) and the typed `RESOURCE_MAP`
  breaks the build on upstream renames, so a surface change cannot ship silently; `npm ci`
  everywhere means the deployed image only changes via a reviewable lockfile diff. The caret
  is a documented design choice, not an oversight.

triaged out during implementation (NaN `PORT`, dropped rationale comments, array-header
tests, `Object.freeze` on shared schemas, `annotate` exhaustive switch, sample
compaction, cache-key alias canonicalisation, fire-and-forget `close()`, README ordering,
etc.) remain reasonable to defer at this size. The one I am re-prioritising **upward** is
item 13 (cross-request isolation test), now folded into rank 6, because the yayson-store
